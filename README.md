# وب‌سایت نماد نیرو

سایت شرکت نماد نیرو — ساخته‌شده با [Astro](https://astro.build) و SQLite. بدون وردپرس، بدون PHP.

محتوای سایت از **پنل مدیریت** (`/admin`) ویرایش می‌شود؛ برای عوض کردن قیمت، عکس، مقاله یا متن‌های سایت نیازی به کدنویسی و انتشار دوباره نیست.

برای انتشار روی سرور، [`DEPLOY.md`](./DEPLOY.md) را ببینید.

---

## اجرا روی سیستم خودتان

نصب دیتابیس لازم نیست: کل دیتابیس یک فایل SQLite است که در پوشهٔ `.data/` ساخته می‌شود. محیط توسعه و سرور دقیقاً یک موتور را اجرا می‌کنند و فقط مسیر فایل فرق می‌کند.

```bash
npm install
npm run db:seed                                    # انتقال محتوا به دیتابیس (فقط بار اول)
npm run db:admin -- you@namadniroo.ir "نام شما"    # ساخت کاربر پنل؛ رمز چاپ می‌شود
npm run dev                                        # http://localhost:4321
```

| دستور | کار |
|---|---|
| `npm run dev` | اجرای محیط توسعه |
| `npm run build` | ساخت نسخهٔ نهایی در `dist/` |
| `npm start` | اجرای همان چیزی که روی سرور اجرا می‌شود |
| `npm test` | اجرای تست‌ها |
| `npm run db:seed` | انتقال محتوای فایل‌محور به دیتابیس |
| `npm run db:admin` | ساخت کاربر پنل یا تغییر رمزش |
| `npm run db:generate` | ساخت فایل مایگریشن بعد از تغییر `schema.ts` |
| `npm run db:backup` | کپی گرفتن از فایل دیتابیس |

## ویرایش محتوا

همه‌چیز از پنل انجام می‌شود؛ این بخش‌ها در `/admin` هستند:

| بخش | چه چیزی |
|---|---|
| **درخواست‌ها** | لیدهای فرم سایت، با وضعیت پیگیری، جست‌وجو و خروجی CSV |
| **محصولات** | فروشگاه — نام، مشخصات، تصویر، ترتیب، سئو |
| **پروژه‌ها** | کارنامهٔ پروژه‌ها |
| **مقالات** | مجله؛ متن با مارک‌داون نوشته می‌شود |
| **تصاویر** | آپلود تصویر؛ تبدیل خودکار به WebP در چند اندازه |
| **متن‌های سایت** | منو، آمار، حوزه‌ها، برندها، کارفرمایان، خط زمانی |
| **سلامت سئو** | بررسی خودکار عنوان تکراری، توضیح غایب، تصویر بدون alt و… |
| **ریدایرکت‌ها** | انتقال نشانی‌های قدیمی |

نقش کاربران: `admin` (همه‌چیز)، `editor` (فقط محتوا)، `sales` (فقط درخواست‌ها).

## معماری

```
src/
├── server/              همهٔ منطق سمت سرور
│   ├── db/              schema، مایگریشن‌ها، اتصال
│   ├── analytics/       ردیابی بازدید، تشخیص کانال، کوئری‌های گزارش
│   ├── repos/           کوئری‌ها — خواندن داده
│   ├── services/        منطق کسب‌وکار — ثبت درخواست، ذخیرهٔ محتوا، صف ایمیل
│   ├── media/           آپلود و بهینه‌سازی تصویر
│   ├── auth/            رمز، سشن، نقش‌ها
│   ├── cache/           کش تگ‌دار
│   └── validation/      اعتبارسنجی ورودی
├── pages/               صفحات سایت و پنل
├── components/          اجزای تکرارشونده
├── layouts/             Base (سایت) و Admin (پنل)
├── data/siteContent.ts  مقدار پیش‌فرض متن‌های سایت
└── styles/              global.css (سایت) و admin.css (پنل)
```

### چند تصمیم که خوب است بدانید

**چرا SQLite.** حجم داده چند مگابایت است و خواندن بسیار بیشتر از نوشتن. کوئری بدون رفت‌وبرگشت شبکه انجام می‌شود، پس از یک دیتابیس شبکه‌ای هم سریع‌تر است — و هزینهٔ ماهانهٔ جدا ندارد. در ازایش بکاپ خودکار ندارد و فایل دیتابیس باید دوره‌ای کپی شود (`DEPLOY.md`). اگر روزی حجم نوشتن خیلی بالا رفت، لایهٔ `repos/` تنها جایی است که باید عوض شود.

**کش تگ‌دار.** هر کوئری با یک برچسب (`products`، `settings` و…) کش می‌شود و هر نوشتن در پنل آن برچسب را باطل می‌کند. نتیجه: سرعت تقریباً برابر با سایت استاتیک، ولی محتوا بلافاصله بعد از ذخیره تازه است. کش زمان‌محور این خاصیت را ندارد.

**صف ایمیل (Outbox).** فرم فقط یک ردیف در صف می‌گذارد و فوراً پاسخ می‌دهد؛ یک worker پس‌زمینه ایمیل را می‌فرستد و در صورت خطا با فاصلهٔ فزاینده دوباره تلاش می‌کند. اگر SMTP از کار بیفتد، هیچ درخواستی گم نمی‌شود.

**آنالیتیکس اول‌شخص.** بازدیدها در `middleware.ts` سمت سرور ثبت می‌شوند و نه با اسکریپت مرورگر: مسدودکننده‌های تبلیغات نمی‌توانند خاموشش کنند، چیزی به زمان بارگذاری صفحه اضافه نمی‌شود، و آمار همان چیزی است که سرور واقعاً سرو کرده. فقط رویدادهایی که سرور نمی‌بیند (کلیک روی شماره، مرحلهٔ ماشین‌حساب، رها کردن فرم) از `components/Analytics.astro` به `/api/track` می‌روند. شناسهٔ بازدیدکننده کوکی `httpOnly` تصادفی است؛ نه آی‌پی ثبت می‌شود نه هیچ دادهٔ شخصی دیگری.

**تصاویر.** Astro فقط تصاویری را می‌تواند بهینه کند که در زمان build داخل مخزن باشند. تصویری که ویراستار آپلود می‌کند بعد از build می‌آید، پس همان لحظه به WebP در چهار اندازه تبدیل و روی دیسک پایدار ذخیره می‌شود. نام فایل از محتوایش ساخته می‌شود، پس کش مرورگر می‌تواند دائمی باشد.

**محافظت از پنل در middleware است، نه در قالب.** قالب یک کامپوننت است و `return` داخلش جلوی رندر صفحه را نمی‌گیرد. این‌طور، صفحهٔ تازه‌ای که به پنل اضافه شود نمی‌تواند به‌اشتباه محافظت‌نشده بماند.

**`site.ts` و `siteContent.ts`.** دومی فقط متن است بدون هیچ تصویری، تا اسکریپت‌های خط فرمان بتوانند بخوانندش؛ اولی تصاویر را به آن می‌چسباند. صفحات همیشه از `site.ts` می‌خوانند.

### تغییر ساختار دیتابیس

```bash
# ۱. src/server/db/schema.ts را عوض کنید
npm run db:generate      # فایل SQL تازه در src/server/db/migrations/ ساخته می‌شود
# ۲. همان فایل را کامیت کنید
```

مایگریشن‌ها با اولین اتصال به دیتابیس خودکار اجرا می‌شوند.

## آنالیتیکس و پروندهٔ فروش

پنل سه صفحهٔ به‌هم‌وصل دارد:

| صفحه | برای چه |
|---|---|
| `/admin/analytics` | قیف تبدیل، کانال‌ها، صفحه‌های ورود، رویدادها، محتوایی که لید ساخته |
| `/admin/leads/<id>` | پروندهٔ هر درخواست: خط زمانی پیگیری + مسیری که همان آدم در سایت طی کرده |
| `/admin/report` | گزارش ماهانهٔ مدیریت، بر مبنای ماه شمسی، آمادهٔ چاپ و PDF |

**قیف اصلی سایت** ماشین‌حساب خورشیدی است و مرحله‌هایش ثبت می‌شوند:
`بازدید → شروع ماشین‌حساب → دیدن برآورد → باز کردن فرم → ثبت درخواست`.
جایی که بیشترین ریزش را نشان می‌دهد، همان جایی است که باید دست برد.

**انتساب کانال** دو لایه دارد. *اولین برخورد* (از کجا این آدم ما را شناخت) روی
پروندهٔ بازدیدکننده ثبت می‌شود و هرگز بازنویسی نمی‌شود؛ *آخرین برخورد* از خود
رویدادها خوانده می‌شود. گزارش‌ها بر مبنای اولین برخورد شمرده می‌شوند، چون کسی که
از اینستاگرام شناخت و بعد با جست‌وجوی نام شرکت برگشت، مشتری‌ای است که اینستاگرام
آورده.

**چرخهٔ داده.** رویدادهای خام ۱۲۰ روز می‌مانند؛ هر شب خلاصهٔ روزانه در
`daily_stats` نوشته می‌شود و برای همیشه باقی می‌ماند. جمع‌بندی و پاک‌سازی و
هشدارهای پیگیری را یک worker هر شش ساعت اجرا می‌کند (`services/rollup.ts`). برای
اجرای دستی:

```bash
npm run db:rollup              # روزهای جمع‌بندی‌نشده
npm run db:rollup -- 2026-09-19  # یک روز مشخص
```

**هشدارها.** درخواستی که ۶ ساعت بی‌تماس بماند و قرار پیگیری‌ای که سررسید شود،
ایمیل می‌شوند (به `MAIL_TO`). هر هشدار در خط زمانی همان پرونده ثبت می‌شود — که
هم گزارش است هم جلوی تکرار شدنش را می‌گیرد.

**برای اتوماسیون بعدی**، `outbox.kind` از حالا `sms` و `webhook` را می‌پذیرد؛
ردیفشان ثبت می‌شود و روزی که پنل پیامکی وصل شود، فرستاده می‌شوند بدون اینکه
منطق اتوماسیون عوض شود.

**نسبت با گوگل آنالیتیکس.** این دو رقیب هم نیستند. GA4/GTM اگر در «تنظیمات سئو ←
ابزار وبمستر» شناسه‌شان وارد شود همچنان کار می‌کنند و برای هیت‌مپ و ضبط سشن
مفیدند. کاری که این سیستم می‌کند و GA نمی‌تواند، اتصال رفتار سایت به نتیجهٔ فروش
است: وضعیت `won` در پنل ثبت می‌شود، نه در مرورگر کاربر.

## سئو

این موارد خودکارند و نیازی به کار دستی ندارند:

- `canonical` هر صفحه، و تگ‌های اشتراک‌گذاری (Open Graph و Twitter)
- دادهٔ ساختاریافته: `Organization`، `LocalBusiness`، `Product` + `Offer`، `Article`، `BreadcrumbList`
- `sitemap.xml` زنده از دیتابیس، با `lastmod` واقعی هر صفحه و کنار گذاشتن صفحات `noindex`
- ریدایرکت ۳۰۱ خودکار هنگام تغییر نشانی یک مطلب
- ابعاد همهٔ تصاویر، تا چیدمان صفحه هنگام لود نپرد
- ریدایرکت نشانی‌های قدیمی وردپرس (`/product/*`، `/category/*`، `/tag/*` و…)

و این‌ها از پنل قابل تنظیم‌اند: عنوان و توضیح سئوی هر صفحه (با پیش‌نمایش نتیجهٔ گوگل)، تصویر اشتراک‌گذاری، `canonical` دستی، `noindex` و محتوای `robots.txt`.

## نکات فنی

- **راست‌چین (RTL):** سراسر سایت و پنل. جهت حرکت اسلایدرها دستی مدیریت شده است.
- **فونت:** دانا، متغیر (وزن ۱۰۰ تا ۹۰۰)، از `public/fonts/`.
- **رنگ‌های برند:** در `:root` فایل `global.css` — زرد `#FFC41A`، سرمه‌ای `#0A3D5D`.
- **دسترس‌پذیری:** فوکوس با کیبورد، احترام به `prefers-reduced-motion`، الزام متن جایگزین برای تصاویر.
- **کارایی:** پوستر اصلی صفحهٔ اول با `preload` اعلام می‌شود و بقیهٔ تصاویر تنبل بارگذاری می‌شوند. مسیر بحرانی اولین بازدید حدود ۱۷۰ کیلوبایت است.
- **فروشگاه:** فعلاً لیدجن است («استعلام قیمت»). ستون‌های `price`، `sku` و `inStock` در دیتابیس آماده‌اند تا در آینده سبد خرید اضافه شود.
